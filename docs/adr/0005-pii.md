# ADR 0005 – Behandlung personenbezogener Daten

Status: angenommen · Datum: 2026-11-08

## Kontext

Der Titanic-Datensatz ist öffentlich und betrifft verstorbene Personen. Der Server soll aber auch
für echte Personendaten taugen.

## Entscheidung

- `name`, `ticket` und `cabin` gelten als personenbezogen.
- Nur mit Scope `pii` liefern die festen Tools diese Felder; nur dann ist `name_contains` erlaubt.
- Ohne `pii` liest das Repository aus der View `passengers_public`: Die Spalten werden gar nicht
  abgefragt. Zusätzlich filtert das Ausgabemodell `PassengerPublic` sie heraus (zwei Schichten).
- `run_sql` sieht nie PII-Spalten, unabhängig vom Scope (Rolle `titanic_sql`).
- Im Audit-Log werden PII-Parameter maskiert (`<redacted> (n chars)`) [BSI DET.3.3].

## Begründung

Eine Maskierung nur im Code wäre ein einzelner Fehlerpunkt. Wird die Spalte gar nicht gelesen, kann
auch ein Fehler in der Maskierung nichts preisgeben.

## Alternativen

- Pseudonymisierung der Namen (z. B. Hash): verhindert gezielte Suche nicht wirklich und ist für
  den Zweck unnötig. Verworfen.
- Eigene Rolle für PII-Zugriffe: sauberer, aber eine weitere DB-Rolle und ein weiterer Pool;
  bei der geringen Last nicht nötig.

## Konsequenzen

- Feld-Maskierung ist keine Anonymisierung: Über Alter, Fare und Klasse lassen sich auch ohne `pii`
  einzelne Personen herausfiltern, `passenger_id` ist eine stabile Kennung. Bekannte Grenze in
  `docs/SECURITY.md`; Mindestgruppengrößen stehen im Ausblick.
